WIRESHARK · TRAFFIC REVIEW
NETWORK ANALYSISCASE 02

Wireshark: baseline & anomaly review

Compared a baseline capture with a synthetic training capture to identify unusual traffic patterns and record packet-level evidence.

PCAP analysisDisplay filtersDNS / FTP / HTTP

Objective

Establish what routine network traffic looks like, then compare a second lab capture to identify deviations using packet filters, timestamps, endpoints, and protocol evidence.

Observed anomalies in the worksheet

  • Plaintext FTP: a workstation exchanged username and password commands with a lab FTP server; plaintext credentials can be exposed to someone able to observe that traffic.
  • HTTP upload: a workstation sent an HTTP POST containing a file named backup.zip to a lab destination on port 8080. The transfer is observed; authorization and sensitivity are unconfirmed.
  • ARP discovery pattern: one workstation sent a rapid sequence of ARP requests for multiple internal addresses. Host discovery is a possibility, but ARP traffic can also be normal.
  • DNS NXDOMAIN pattern: repeated queries for random-looking subdomains returned NXDOMAIN. This warrants review, but the pattern alone does not establish a domain-generation algorithm or malware.

Limitations

The worksheet describes synthetic lab captures. Classifications are training assessments, not evidence of compromise in a real organization. The worksheet also includes a baseline capture and practice for DNS, TCP handshakes, TLS, retransmissions, and resets.

WEB SECURITYCASE 03

OWASP Juice Shop: directory enumeration

Used Gobuster to discover local web paths, then manually inspected selected directory listings and HTTP responses.

4,750entries enumerated
07documented findings
Gobuster 3.8.2HTTP analysisKali Linux

Objective

Enumerate common web content paths on an intentionally vulnerable local OWASP Juice Shop instance and validate selected responses in an authorized lab.

Key observations

  • Directory listing exposed an inventory of files and a quarantine subdirectory.
  • A file labeled confidential was accessible, although its body contained placeholder text rather than verified business information.
  • Malware-themed .url filenames were visible in a quarantine listing; files were not downloaded or executed.
  • Specific requests returned HTTP 403; a random nonexistent-looking path returned HTTP 200; several routes returned HTTP 500 during enumeration. These status codes require context and do not independently prove vulnerabilities.

Recommendations

Disable public directory indexing, move sensitive artifacts outside the public web root, enforce server-side authorization, use generic client-facing errors, and validate fallback routes and server errors individually.

Assessment scope: local training application at 127.0.0.1:3000. Severity ratings in the report are preliminary.

DEFENSIVE LABCASE 05

Cowrie: SSH honeypot home lab

Ran Cowrie in a Kali Linux VM and validated connectivity from Windows using a VirtualBox Host-Only network.

2222/TCPlistening port
3.1.3Cowrie version
Linux CLIVirtualBoxLog analysis

Objective

Deploy an SSH honeypot in a contained local network, verify the service and port, test client connectivity, and preserve logs of the interaction.

Observed results

  • Cowrie 3.1.3 was running in a Python virtual environment on Kali Linux in Oracle VirtualBox.
  • The service listened on TCP port 2222; Windows PowerShell reported TcpTestSucceeded: True for the host-only test.
  • An SSH session reached Cowrie's emulated Linux shell, and logs recorded connection, simulated login, shell initialization, and commands.
  • A troubleshooting step identified that the client had to specify port 2222 rather than relying on SSH's default port 22.

The root-like prompt and filesystem belong to Cowrie's emulation. The test does not demonstrate access to the underlying Kali system or a production network.

INCIDENT REPORTINGCASE 06

Incident response: scenario reports

Practiced structured incident intake, impact assessment, evidence preservation, corrective actions, and escalation recommendations.

Ransomware scenarioUnauthorized accessIncident documentation

Scenario B — IR-002: Ransomware notice

The exercise describes a user seeing a ransom message after attempting to open a spreadsheet, with the desktop wallpaper changed. The report records a high-category suspected ransomware incident, ongoing interruption, and unknown exact start time.

Recommended actions include immediate escalation, isolating the device according to policy, preserving the ransom note and system state, avoiding ad hoc cleanup or ransom payment, collecting endpoint/email/network evidence, and assessing recovery from trusted backups.

Scenario C — IR-003: Unauthorized access

The scenario describes an IT alert of account access from an IP geolocated to Romania at approximately 3:00 AM while the employee was asleep. The password had not been changed for two years and was reused across websites. The report recommends verifying the alert in authentication logs, revoking sessions, resetting the password via a trusted device, enabling MFA, and reviewing account changes.

These are scenario-based training reports dated 21 October 2026. They are not claims of real incidents at an organization. Both reports leave missing facts marked as unknown or to be verified.
